호출 여부 분류기 평가에서는 일반 대화를 실행 요청으로 잘못 분류하는 오류와 실제 요청을 놓치는 오류를 함께 확인합니다. 이 문서는 학습에 추가한 사례의 구성에 따라 두 오류가 어떻게 달라졌는지 비교합니다.

## Evaluation setup

비교 실험은 실제 요청 168건과 일반 대화 24건으로 구성된 기존 평가셋을 사용했습니다. 비실행 사례만 보강한 조건과, 같은 기능의 실행·비실행 사례를 함께 보강한 조건을 비교했습니다. 평가 문장과 완전히 겹치는 학습 후보 3건은 제외했습니다. 아래 수치는 개발 중 이미 열람한 평가셋을 재사용한 회고 비교 결과입니다.

| 학습 구성 | 일반 대화의 잘못된 호출 후보 판정 | 실제 요청 재현율 | 호출 여부 분류 정확도 |
| --- | --- | --- | --- |
| 초기 3i4K 기반 MLP | 16/24 (66.67%) | 163/168 (97.02%) | 89.06% |
| 한국어 비실행 사례 보강 | 2/24 (8.33%) | 118/168 (70.24%) | 72.92% |
| 기능별 실행·비실행 사례를 함께 보강 | 2/24 (8.33%) | 160/168 (95.24%) | 94.79% |
| 위 구성에 한국어 비실행 사례 추가 | 1/24 (4.17%) | 159/168 (94.64%) | 94.79% |

비실행 사례만 보강한 조건은 잘못된 호출을 줄이면서 정상 요청도 많이 거절했습니다. 기능별 실행·비실행 사례를 함께 보강한 두 조건은 전체 정답 수가 같지만 오류 구성이 다릅니다. 마지막 조건은 잘못된 호출을 한 건 줄이는 대신 정상 요청을 한 건 더 놓쳤습니다.

임베딩 기준선에서 일반 대화를 호출 후보로 잘못 판정한 비율은 11/24(45.83%)였으며, 마지막 MLP 후보는 1/24(4.17%)였습니다. 평가 범위는 호출 후보 판정까지이며, 이후 인자 생성과 사용자 확인을 거친 실제 기능 실행 성공률은 포함하지 않습니다.

<summary>Dataset and integration scope</summary>

개발 중 이미 열람한 Holdout을 재사용했습니다. Dev와 Holdout 사이에도 같은 문장 8건이 있으므로 두 점수를 독립적인 검증 결과로 취급하지 않습니다.

제품의 iOS·Android 공통 코어는 호출 여부 MLP를 통과한 입력에 한국어 규칙과 임베딩 선택기를 적용합니다. 위 표는 당시 분류기 후보의 회고 비교이며, 이후 추가된 현재 시각 조회나 수정된 라우팅 전체의 최신 점수로 해석하지 않습니다.
