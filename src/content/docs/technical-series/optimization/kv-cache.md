대화 런타임은 매 요청의 전체 입력을 구성하고, 기존 세션에서 토큰이 일치하는 접두부의 KV 캐시를 재사용합니다. 완료된 대화의 추론 상태는 파일에 저장하며, 새 세션을 준비할 때 복원합니다. 현재 캐시 어댑터는 LiteRT-LM의 CPU 백엔드와 Gemma 4 텍스트 입력을 대상으로 합니다.

## Dialogue History and Inference State

앱의 대화 이력은 다음 요청에 포함할 메시지를 결정합니다. 네이티브 세션은 모델이 입력을 처리하면서 만든 KV 텐서와 처리 위치를 보관합니다. 두 상태의 수명은 다릅니다. 세션을 해제하거나 캐시 파일을 삭제해도 앱은 보관한 대화 이력으로 다음 입력을 구성할 수 있습니다.

입력에는 대화 지침, 최근 대화와 검색한 기억이 포함됩니다. 검색 결과나 지침이 바뀌고 오래된 메시지가 빠질 수 있으므로, 새 질문을 기존 입력 뒤에 계속 덧붙이지 않고 요청마다 전체 입력을 교체합니다.

## Full-Prompt Replacement

`prepareDialogue`는 입력을 구성하고 토큰 예산을 확인한 뒤 캐시 세션을 준비합니다. 샘플링 설정과 출력 상한이 같으면 기존 세션을 유지하고, 달라지면 새 세션을 만듭니다. `replaceInput`은 이번 요청의 지침을 설정하고 이전 요청의 재시도 이력을 비웁니다.

입력 제출 전에는 `session_rewind_to_step(0)`으로 처리 위치를 되돌립니다. 이 호출은 KV 버퍼를 지우지 않습니다. 이후 전체 입력을 전달하면 LiteRT-LM의 접두부 비교가 동일한 토큰을 건너뛰고 달라진 구간부터 처리합니다. 입력 구성부는 공통 지침과 출력 형식처럼 세션 동안 유지되는 부분을 앞에 모으고, 요청마다 바뀌는 지침과 문맥을 뒤에 배치합니다. 앞부분의 지침이 바뀌면 재사용할 수 있는 접두부도 짧아집니다.

생성 중에는 입력 교체와 되감기를 허용하지 않습니다. 취소를 요청한 경우에도 네이티브 콜백이 종료될 때까지 세션을 유지합니다. 같은 요청 안에서 발생한 재시도는 앞선 화면 출력과 함께 공식 대화 템플릿으로 입력을 구성합니다.

## State Transfer

`litert_lm_session_transfer_state`는 유휴 상태의 CPU 세션과 호출자 사이에서 추론 상태를 동기적으로 전달합니다. 네이티브 계층은 세션의 독점 사용과 작업 종료를 확인하고, Swift 파일 처리부가 버퍼를 읽거나 채우도록 콜백을 호출합니다.

전송 대상은 KV 텐서, 처리 위치, 처리한 토큰 ID, 대기 토큰의 임베딩과 샘플러 상태입니다. 복원은 새 세션에서 수행하며, 다음 요청의 전체 입력을 제출하기 전에 끝납니다. 생성 중이던 답변을 중간부터 이어가는 용도로 사용하지 않습니다.

콜백에 전달하는 버퍼는 최대 64KiB이며 호출이 진행되는 동안에만 유효합니다. 파일 처리부는 이 버퍼를 직접 읽고 쓰므로 전체 KV를 별도의 저장용 버퍼에 복제하지 않습니다. 파일명, 체크섬과 파일 교체 정책은 Swift의 `KVCheckpointStore`가 관리합니다.

## Checkpoint Lifecycle

앱은 완료된 대화를 이력에 반영한 뒤 최신 체크포인트 하나를 저장합니다. 취소, 오류, 도구 응답과 메모리 캡션 세션은 저장을 시작하지 않습니다. 파일은 임시 경로에 작성하고 쓰기가 끝나면 기존 파일을 교체합니다. 쓰기 실패 시 이전 캐시와 완료된 대화 이력은 유지됩니다.

복원 시 파일의 호환성 버전, 모델 파일명, 컨텍스트 용량과 페이로드 체크섬을 검사합니다. 모델 파일을 명시적으로 가져오는 경로는 같은 파일명으로 교체하더라도 기존 캐시를 삭제합니다. 대화 초기화와 기억 삭제도 캐시를 삭제합니다. 프롬프트 변경은 파일 전체를 무효화하지 않으며, 복원 이후 토큰 접두부 비교로 재사용 범위를 정합니다.

파일이 손상되거나 호환되지 않으면 일부 복원된 상태를 비우고 입력 전체를 다시 계산합니다. 상태 정리에 실패하면 해당 세션에서 추론을 거부하고 엔진을 다시 준비해야 합니다.

저장과 복원 중에는 파일 입출력과 체크섬 계산이 발생하고 세션을 다른 추론 작업에 사용할 수 없습니다. 성능을 비교할 때는 이 비용과 프리필 재계산 시간을 함께 측정합니다.

## Pending Tokens After Rewind

되감기 이후의 대기 토큰에는 ID만 남아 있을 수 있습니다. 실수형 임베딩을 입력받는 실행 경로는 프리필 전에 `EnsurePendingPrefillEmbeddings`를 호출해 일반 임베딩과 필요한 레이어별 임베딩을 준비합니다.

이미 존재하는 값은 유지하고 누락된 값만 조회합니다. 조회 실패나 빈 결과는 오류로 반환합니다. 관련 테스트는 ID만 있는 토큰, 레이어별 임베딩만 누락된 토큰, 조회 실패 후 재시도와 기존 값 보존을 다룹니다.

## Restoration Validation

Mac CPU 통합 검증은 실제 앱의 입력 구성 코드와 상태 전송 API를 사용합니다. 서로 다른 프로세스에서 체크포인트를 저장하고 복원한 뒤, 탐욕적 디코딩의 화면 출력을 처음부터 계산한 결과와 비교합니다.

| 조건 | 결과 |
| --- | --- |
| 다음 대화 | 출력 일치 |
| 동적 입력 변경 | 출력 일치 |
| 최근 대화 보관 범위 변경 | 출력 일치 |
| 취소하거나 실패한 대화 이후 | 기존 캐시 보존, 후속 출력 일치 |
| 손상, 잘림, 구형 형식, 호환 불일치 파일 | 재계산 후 출력 일치 |
| 아이폰의 첫 응답 시간, 저장·복원 시간과 메모리 피크 비교 | 미측정 |

## Metrics

요청별 응답 시간은 런타임의 `first_response_seconds`로 기록합니다. 네이티브 TTFT는 세션의 첫 번째 턴을 기준으로 하므로 후속 요청의 응답 시간으로 사용하지 않습니다.

`matchingInputPrefixTokens`는 두 입력 사이의 접두부 일치 토큰 수입니다. 세션 C API가 실제 KV 크기를 제공하지 않으므로 이 값을 KV 적중 수로 해석하지 않습니다.
