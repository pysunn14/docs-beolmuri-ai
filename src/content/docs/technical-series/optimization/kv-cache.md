대화 런타임은 매 요청의 전체 입력을 구성하고, 기존 세션에서 토큰이 일치하는 접두부의 KV 캐시를 재사용합니다. 완료된 대화의 추론 상태는 파일에 저장하며, 새 세션을 준비할 때 복원합니다. 제품은 iOS의 CPU와 Android의 CPU·GPU 경로에서 캐시 세션을 사용합니다. 체크포인트는 백엔드와 엔진 식별자가 일치할 때만 복원합니다.

## Dialogue history and inference state

앱의 대화 이력은 다음 요청에 포함할 메시지를 결정합니다. 네이티브 세션은 모델이 입력을 처리하면서 만든 KV 텐서와 처리 위치를 보관합니다. 두 상태의 수명은 다릅니다. 세션을 해제하거나 캐시 파일을 삭제해도 앱은 보관한 대화 이력으로 다음 입력을 구성할 수 있습니다.

입력에는 대화 지침, 최근 대화와 검색한 기억이 포함됩니다. 검색 결과나 지침이 바뀌고 오래된 메시지가 빠질 수 있으므로, 새 질문을 기존 입력 뒤에 계속 덧붙이지 않고 요청마다 전체 입력을 교체합니다.

## Full-prompt replacement

`prepareDialogue`는 입력을 구성하고 토큰 예산을 확인한 뒤 캐시 세션을 준비합니다. 샘플링 설정과 출력 상한이 같으면 기존 세션을 유지하고, 달라지면 새 세션을 만듭니다. `replaceInput`은 이번 요청의 지침을 설정하고 이전 요청의 재시도 이력을 비웁니다.

입력 제출 전에는 `session_rewind_to_step(0)`으로 처리 위치를 되돌립니다. 이 호출은 KV 버퍼를 지우지 않습니다. 이후 전체 입력을 전달하면 LiteRT-LM의 접두부 비교가 동일한 토큰을 건너뛰고 달라진 구간부터 처리합니다. 재사용할 접두부를 정한 뒤 처리 위치도 그 끝에 맞춰야 새 토큰이 기존 KV를 덮어쓰지 않습니다. 입력 구성부는 공통 지침과 출력 형식처럼 세션 동안 유지되는 부분을 앞에 모으고, 요청마다 바뀌는 지침과 문맥을 뒤에 배치합니다. 앞부분의 지침이 바뀌면 재사용할 수 있는 접두부도 짧아집니다.

생성 중에는 입력 교체와 되감기를 허용하지 않습니다. 취소를 요청한 경우에도 네이티브 콜백이 종료될 때까지 세션을 유지합니다. 같은 요청 안에서 발생한 재시도는 앞선 화면 출력과 함께 공식 대화 템플릿으로 입력을 구성합니다.

## State transfer

네이티브 확장의 소스는 [LiteRT-LM 공개 포크의 고정 커밋](https://github.com/mornye-minor-gallery/LiteRT-LM/tree/939b09f5ac92974bb4a7df430d440c2b8780941e)에 있습니다. 원본 커밋 `a327b494`를 기준으로 CPU 상태 전송과 대기 토큰의 프리필 복구를 구현했으며, 원본의 기존 주석은 유지합니다. [수정 범위와 API 계약](https://github.com/mornye-minor-gallery/LiteRT-LM/blob/939b09f5ac92974bb4a7df430d440c2b8780941e/docs/PETAI_KV_CHECKPOINT.md)에서 변경한 파일과 검증 방법을 확인할 수 있습니다.

공개 포크는 엔진의 상태 전송을 담당합니다. Swift 연결부와 `KVCheckpointStore`의 파일 저장 정책은 앱 저장소에서 관리합니다. 같은 공개 저장소의 `petai-ios-embedding-native-v1` 릴리스는 임베딩용 LiteRT·SentencePiece 프레임워크이며, KV 엔진과는 별개의 의존성입니다.

`litert_lm_session_transfer_state`는 유휴 상태의 세션과 호출자 사이에서 추론 상태를 동기적으로 전달합니다. 네이티브 계층은 세션의 독점 사용과 작업 종료를 확인하고, Swift 파일 처리부가 버퍼를 읽거나 채우도록 콜백을 호출합니다.

전송 대상은 KV 텐서, 처리 위치, 처리한 토큰 ID, 대기 토큰의 임베딩과 샘플러 상태입니다. 복원은 새 세션에서 수행하며, 다음 요청의 전체 입력을 제출하기 전에 끝납니다. 생성 중이던 답변을 중간부터 이어가는 용도로 사용하지 않습니다.

콜백에 전달하는 버퍼는 최대 64KiB이며 호출이 진행되는 동안에만 유효합니다. 파일 처리부는 이 버퍼를 직접 읽고 쓰므로 전체 KV를 별도의 저장용 버퍼에 복제하지 않습니다. 파일명, 체크섬과 파일 교체 정책은 Swift의 `KVCheckpointStore`가 관리합니다. 캐릭터별 대화 파일과 달리 추론 캐시는 백엔드별 경로에 최신 파일 하나를 사용하며, 다른 대화로 전환한 뒤에는 전체 입력의 접두부 일치 범위만 재사용합니다.

## Checkpoint lifecycle

앱은 Unity가 확정한 완료 대화를 이력에 반영한 뒤 최신 체크포인트 하나를 저장합니다. 문맥 요약 후에도 재구성한 입력을 계산하고 캐시를 저장합니다. 취소·오류 요청과 메모리 후보 생성은 일반 대화 체크포인트를 저장하지 않습니다. 도구 응답도 직접 저장하지 않지만, 이후 문맥 정리가 필요하면 정리된 입력의 캐시를 저장할 수 있습니다. 파일은 임시 경로에 작성하고 쓰기가 끝나면 기존 파일을 교체합니다. 쓰기 실패 시 이전 캐시와 완료된 대화 이력은 유지됩니다.

복원 시 파일의 호환성 버전, 모델 파일 내용의 해시, 컨텍스트 용량, 백엔드·엔진 식별자와 페이로드 체크섬을 검사합니다. 모델 파일을 명시적으로 가져오는 경로는 같은 파일명으로 교체하더라도 기존 캐시를 삭제합니다. 대화 초기화와 기억 삭제도 캐시를 삭제합니다. 프롬프트 변경은 파일 전체를 무효화하지 않으며, 복원 이후 토큰 접두부 비교로 재사용 범위를 정합니다.

파일이 손상되거나 호환되지 않으면 일부 복원된 상태를 비우고 입력 전체를 다시 계산합니다. 상태 정리에 실패하면 해당 세션에서 추론을 거부하고 엔진을 다시 준비해야 합니다.

저장과 복원 중에는 파일 입출력과 체크섬 계산이 발생하고 세션을 다른 추론 작업에 사용할 수 없습니다. 성능을 비교할 때는 이 비용과 프리필 재계산 시간을 함께 측정합니다.

## Pending tokens after rewind

되감기 이후의 대기 토큰에는 ID만 남아 있을 수 있습니다. 실수형 임베딩을 입력받는 실행 경로는 프리필 전에 `EnsurePendingPrefillEmbeddings`를 호출해 일반 임베딩과 필요한 레이어별 임베딩을 준비합니다.

이미 존재하는 값은 유지하고 누락된 값만 조회합니다. 조회 실패나 빈 결과는 오류로 반환합니다. 관련 테스트는 ID만 있는 토큰, 레이어별 임베딩만 누락된 토큰, 조회 실패 후 재시도와 기존 값 보존을 다룹니다.

## Restoration validation

Mac CPU 통합 검증은 실제 앱의 입력 구성 코드와 상태 전송 API를 사용합니다. 서로 다른 프로세스에서 체크포인트를 저장하고 복원한 뒤, 탐욕적 디코딩의 화면 출력을 처음부터 계산한 결과와 비교합니다.

| 조건 | 결과 |
| --- | --- |
| 다음 대화 | 출력 일치 |
| 동적 입력 변경 | 출력 일치 |
| 최근 대화 보관 범위 변경 | 출력 일치 |
| 취소하거나 실패한 대화 이후 | 기존 캐시 보존, 후속 출력 일치 |
| 손상, 잘림, 구형 형식, 호환 불일치 파일 | 재계산 후 출력 일치 |
| 아이폰의 파일 저장·복원 시간과 복원 전후 메모리 피크 비교 | 미측정 |

## iPhone cache ablation

메모리에 남은 KV를 재사용했을 때 대기 시간이 얼마나 줄어드는지 확인하기 위해, iPhone 17에서 요청마다 새 세션을 만드는 방식과 캐시 세션을 유지하는 방식을 비교했습니다. 같은 5턴 대화를 조건별로 3회 실행했으며, 총 30개 요청을 측정했습니다. 첫 요청은 캐시를 채우는 단계이므로 후속 요청과 나누어 집계했습니다.

| 측정값 | 요청마다 새 세션 | 캐시 세션 재사용 |
| --- | ---: | ---: |
| 전체 평균 TTFT, 조건별 15개 요청 | 4.920초 | 1.274초 |
| 후속 요청 평균 TTFT, 조건별 12개 요청 | 4.872초 | 0.446초 |
| 후속 요청 평균 TPOT | 39.29ms | 38.39ms |

첫 출력을 받기까지 걸린 시간은 전체 평균 74.1%, 후속 요청 평균 90.8% 줄었습니다. 반면 첫 요청의 TTFT 중앙값은 각각 4.570초와 4.617초로 비슷했습니다. 토큰당 생성 시간인 TPOT도 큰 차이가 없어, 이번 조건에서는 캐시 재사용의 효과가 답변 생성을 시작하기 전 대기에 집중됐습니다. 비교한 답변 15쌍은 문자열까지 일치했습니다.

### Measurement setup

2026년 9월 29일, iOS 26.6.2의 별도 측정 앱에서 제품과 같은 Swift 대화 런타임과 프롬프트 조립기를 사용했습니다. 모델은 Gemma 4 E2B, 추론 엔진은 LiteRT-LM CPU 백엔드이며 컨텍스트는 4,096토큰, 최대 출력은 128토큰으로 설정했습니다. 샘플링은 temperature 0.7, top-k 40, top-p 1.0이고 thinking은 껐습니다.

입력은 고정 시스템 지침과 미리 작성한 대화 이력으로 구성했습니다. 검색은 끄고, 두 조건에 같은 입력을 전달했습니다. 실행 순서는 캐시 끔→켬, 켬→끔, 끔→켬으로 바꿨습니다. 전체 평균은 첫 요청 1개와 후속 요청 4개로 구성된 이 시나리오의 결과이며, 재사용 가능한 접두부 길이와 대화 길이에 따라 달라집니다.

[요청별 측정값과 집계 조건 JSON](evidence/kv-cache-iphone-20260929.json)에는 30개 요청의 수치, 모델·빌드 식별값과 출력 일치 검증 결과를 담았습니다. 평균은 요청별 측정값의 산술평균이며, 감소율은 `100 × (1 - 재사용 평균 / 새 세션 평균)`으로 계산합니다.

## Metrics

위 실험의 TTFT는 런타임의 생성 요청부터 첫 비어 있지 않은 출력 조각까지의 시간인 `first_response_seconds`입니다. 기억 저장 판정인 `save(...)` 헤더도 출력에 포함되므로 화면에 첫 대사가 표시되는 시간과는 구분합니다. 모델 초기화와 입력 준비는 이 측정 구간 밖입니다. 네이티브 TTFT는 세션의 첫 번째 턴을 기준으로 하므로 후속 요청의 응답 시간으로 사용하지 않습니다.

TPOT는 네이티브가 기록한 요청별 decode 처리량의 역수로 계산합니다. `1,000 / 초당 생성 토큰 수`가 토큰당 밀리초입니다. 위 비교는 실행 중인 세션의 KV 재사용을 다루며, 파일 체크포인트의 저장·복원 비용은 별도로 측정합니다.

`matchingInputPrefixTokens`는 두 입력 사이의 접두부 일치 토큰 수입니다. 세션 C API가 실제 KV 크기를 제공하지 않으므로 이 값을 KV 적중 수로 해석하지 않습니다.
